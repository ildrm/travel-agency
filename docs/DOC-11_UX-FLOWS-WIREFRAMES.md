# DOC-11 — UX flows, screens and wireframes

**Status:** DRAFT specification; review pending. **Purpose:** specify key screen contracts for design and implementation. **Prepared from perspectives:** UX, operations, accessibility, localization, Woo engineering. **Accountable reviewer:** product design lead. **Dependencies:** [IA](DOC-10_INFORMATION-ARCHITECTURE.md), [design system](DOC-12_DESIGN-SYSTEM-UI-KIT.md), [booking](DOC-24_BOOKING-INVENTORY-REGISTRATION.md). **Approval gate:** product, operations and accessibility reviewers approve critical paths and test evidence.

## 1. Shared screen behavior

Every screen has one labeled H1, language switch, logical heading/focus order and a reachable support route. Mobile uses a single column with full-width primary action; desktop uses a content column and, where space permits, a non-obscuring summary. Inputs have persistent labels, instructions and associated errors; summaries link to fields, server errors preserve valid entries, and loading/disabled/success are expressed in text. A disabled visual control never replaces server validation. Respect RTL and isolate numbers, references and email addresses. Consent is explicit where required and separate from marketing. Times carry a named zone, prices identify IRR/toman. Analytics records IDs and outcome only, never form content or traveler PII.

## 3. Annotated wireframes

**UI-REG-001 mobile**
```text
[Header: menu | brand | language | account]
[Breadcrumb] [H1: occurrence title]
[Status: Registration opens 1 June, 09:00 Asia/Tehran]
[Date/time and venue] [Access details] [Program and terms]
[Included / excluded] [Price: amount + IRR or toman]
[Quantity] [Eligibility help + error if needed]
[Sign in / Reserve] [Support link]
```
On desktop use a main details column and secondary price/booking summary; on tablet place summary after description. At 200% zoom summary must not obscure content. Screen receives API-CAT-001 for public metadata and API-BOOK-001 for hold; server returns explicit closed/sold-out/validation codes. Focus goes to an error summary on submit failure. `TC-REG-001/002` cover boundaries and contention.

**UI-COM-001 mobile**
```text
[H1 Checkout] [Payment deadline: absolute time and countdown]
[Order summary, quantity, inclusions/exclusions]
[Purchaser contact] [Required traveler details]
[Delivery address only for physical product]
[Terms checkbox + full policy link]
[Payment method: eligible hosted gateway]
[Total: IRR amount and clearly labeled toman if shown]
[Pay securely] [Support] [Save or return]
```
The fixed deadline comes from server; visual timer is informational. At the hold deadline, block new payment initiation and offer restart only when admission remains open; if payment may already be in flight, show review status. The allocation remains until a serialized consume/release decision, not necessarily until the displayed countdown alone. Do not silently remove incompatible items. API-PAY-001 handles proposed callback; Woo checkout extension points are subject to version verification.

## 4. Interaction tests and open decisions

Keyboard users reach all controls in order and see a focus ring; error summary and headings work in EN/FA at 320 CSS px, zoom and text enlargement. Screen readers get clear loading and status messages without repeated countdown announcements. Owners must decide exact field schema per offering, contact verification, privacy basis and translation fallback. No user tests or accessibility audit have yet been performed; approve production copy and legal terms before launch.

**Self-assessment (0–5):** completeness 4 (representative critical and later screens); specificity 4 (field/state matrix); consistency 4 (shared deadlines); user value 4 (recovery paths); WP feasibility 4 (Woo extension dependency); security/privacy 4 (scoping/minimization); compliance 2 (content and provider approval missing, blocker); accessibility/localization 4 (behavior specified); testability 4 (cases); traceability 4 (screen/FR/API links). Further component-level field validation remains a design review task.


## 5. Detailed screen and field specifications

**Applies to each row:** show skeleton with an announced loading label, a retryable error that preserves input, a meaningful empty state and a textual success state. Server is authoritative for data, ownership, inventory and prices. Mobile is a single column with primary action after context; tablet places filters and cards in a collapsible side area when space permits; desktop adds non-sticky or safely bounded secondary summary. At narrow width and enlarged text no action or message is clipped. Every input has an associated visible label and help/error; focus moves to error summary after submission, and keyboard navigation, language/direction and alternative status text are mandatory. Capture only approved event name, screen ID, locale and outcome; no text fields, traveler names, payment details or sensitive selections in analytics. Permission denial and missing dependency are visible and must not disclose record details. The event labels below are unapproved instrumentation proposals, not implemented tracking. Do not deploy or collect them until their purpose, data fields, consent and retention are approved and each label is registered or mapped to an approved event in [DOC-42](DOC-42_ANALYTICS-OBSERVABILITY-KPIS.md).
