# DOC-33 — Flights, rail and bus ticketing

**Status:** DRAFT specification; review pending. **Purpose:** distinguish inquiry, supplier reservation and issued ticket. **Prepared from perspectives:** ticketing, supplier integration, support and finance. **Accountable reviewer:** passenger ticketing lead. **Dependencies:** [DOC-24](DOC-24_BOOKING-INVENTORY-REGISTRATION.md), [DOC-26](DOC-26_APIS-INTEGRATION-CONTRACTS.md), [DOC-37](DOC-37_PAYMENTS-DOMESTIC-GATEWAYS.md). **Decision:** MVP is request-only without live inventory or payment; phase 3 integration requires a licensed supplier agreement, tested sandbox and operational support. All provider behavior below is proposed, not claimed.

## 1. Domain and workflows
**FR-AIR-001 / FR-GROUND-001:** collect routes, departure/arrival location, local dates/time zones, traveler count, fare class, baggage and accessibility needs in an inquiry. ENT-QUOTE holds source, retrieved time, expiry, currency, fare components, terms and freshness; ENT-TRAVELER contains necessary identity matched to ticketing rules; ENT-BOOKING holds local state; ENT-TICKET holds issuer reference and issuance status separately from ENT-ORDER and ENT-PAYMENT. Supplier reservation locator, passenger information and travel documents are restricted. Retain only documented necessary identity fields and apply deletion/legal hold policy.

**WF-TICKET-001 (future integration):** search supplier → show tentative quote and restrictions → reprice/recheck → acquire supplier hold if actually supported → collect verified payment → request issuance → inspect authoritative issuance result → confirm ticket or open exception. Supplier state, payment verification, Woo order and fulfillment remain independent. A redirect or successful order cannot prove issuance. No DB transaction spans a supplier call: persist request and outbox, use idempotency where supplier supports it, handle ambiguous timeouts by inquiry/reconciliation rather than blindly creating a second reservation. Supplier-specific seat maps, refunds, PNR and revalidation are available only where contract and capability evidence support them. Customer changes and disruption notices enter support queue; not all supplier changes are self-service.

**UI-TICKET-001** displays request-only notice in MVP: “Availability must be confirmed” / «موجودی باید تأیید شود». Future results show freshness, price expiry, carrier/operator, all fees, baggage, change/refund conditions and names required. **API-TICKET-001** proposed `POST /agency/v1/ticket-requests` creates inquiry; future adapter contracts expose abstract search/quote/reservation/issuance/status/cancel semantics, with actual mapping unresolved. Public calls cannot enumerate another customer’s references. Assigned ticketing staff see passenger data only for service delivery; user sees their own request, finance sees amounts but not documents. Never log identity documents or secrets.

## 2. Fictional scenario F — payment succeeds, flight issuance fails
Proposed/mock integration only; no licensed or live supplier exists. User searches Tehran–destination, one adult, receives illustrative fare 50,000,000 IRR, expires in five minutes; fare, tax and baggage terms appear. Customer signs in, reviews passenger name and accepts restrictions. Future contracted supplier confirms a reservation/hold; payment is independently verified for 50,000,000 IRR and Woo order is paid. Issuance request times out, then a provider status check returns failure. Booking remains `exception`, not confirmed; ENT-TICKET is not issued; outbox raises an operations task and customer sees “Payment received; ticket not yet issued” / «پرداخت دریافت شد؛ بلیت هنوز صادر نشده است». Assigned agent checks authoritative status, tells customer, requests consent for an alternative or approves refund under contract; finance submits and reconciles refund separately. Notification contains no passport number. The reservation and issue methods are hypothetical abstractions and require actual provider mapping, not asserted APIs.

| Exception | Handling and financial outcome |
|---|---|
| Fare changes before acceptance | Requote with expiry; customer explicitly accepts new total or abandons with no payment. |
| Supplier reservation rejected | Do not request payment; show unavailable, retry with a fresh quote only. |
| Payment verifies after hold release | Transition booking `expired → exception` with prior expiry audited; allocation remains released and payment remains verified. No new admission or automatic issue; queue manual resolution/refund. |
| Issue call times out | Mark unknown, query supplier; avoid duplicate issue; operator resolves and logs. |
| Duplicate issue callback | Correlate identifiers/idempotency; apply once, reconcile any unexpected second document. |
| Wrong traveler data | Block or route to authorized correction per verified supplier terms; explain fees before consent. |
| Disruption, cancellation or chargeback | Notify affected customer, route to operations and finance; refund/chargeback state separate from ticket state. |

## 3. Tests and open decisions
**TC-TICKET-001:** paid order with failed issuance never appears as ticket issued; **TC-TICKET-002:** ambiguous timeout does not issue twice; **TC-TICKET-003:** stale fare requires fresh acceptance; **TC-AUTH-001:** other organization cannot retrieve traveler data. Test rail/bus operators with no seat maps, station time-zone changes, supplier downtime, partial group issue, duplicate webhook and reconciliation. Aggregate search-to-request, issue-failure and time-to-resolution without identity in analytics. **OPEN DECISION:** ticketing lead must secure credentials, sandbox, availability and fare contracts, dispute and refund rights, support SLA, licensing and production certification; none are confirmed. Acceptance requires realistic supplier contract tests before enabling a route.

## 4. Supplier acceptance checklist
Before phase-3 implementation, ticketing and procurement obtain permission to sell the relevant routes, fare display and tax rules, ticket issuance rights, refund/change procedures, support hours, settlement method and sandbox-to-production acceptance criteria. Engineering maps each documented supplier operation to an internal adapter capability and distinguishes supported, unavailable and unknown. Search results must show when fetched and when quote validity expires, identify whether baggage or seat selection costs extra, and prevent claims of a guaranteed fare from a stale cached result. On post-payment ambiguity, staff check whether a reservation or ticket actually exists with the supplier before attempting compensation; a customer must not be charged twice while a previous outcome is unknown. Any passenger data exported to a supplier is restricted to fields required by the verified agreement. A rail or bus operator may have no seat-selection capability: the UI must omit the selection rather than synthesize a seat map. Airline, rail and bus commercial rules remain separate because changes, refunds and disruption responsibilities depend on the actual supplier agreement.
