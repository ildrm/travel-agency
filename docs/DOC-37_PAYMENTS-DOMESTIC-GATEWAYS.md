# DOC-37 — Domestic payment gateways

**Status:** DRAFT specification; review pending. **Purpose:** define verified payments and due diligence for a domestic gateway. **Prepared from perspectives:** WooCommerce engineering, finance, security and support. **Accountable reviewer:** payment integration lead. **Dependencies:** [DOC-24](DOC-24_BOOKING-INVENTORY-REGISTRATION.md), [DOC-25](DOC-25_WOOCOMMERCE-COMMERCE-ENGINE.md), [DOC-39](DOC-39_FINANCE-PRICING-SETTLEMENTS.md). **Decision:** MVP selects one eligible, verified gateway after review; SEP/Saman, Behpardakht Mellat and ZarinPal are candidates only, not assumed contracted, compatible or technically verified (ADR-009).

## 1. Data, states and due diligence
**FR-PAY-001:** ENT-PAYMENT stores order/booking references, attempt ID, configured provider, exact expected integer IRR amount, request and response correlation identifiers, state (`created → pending → verified/failed/unknown`), trusted provider payment time if available and verification evidence reference. `verified` is monotonic; ENT-REFUND has its own `requested → approved → submitted → succeeded/failed` lifecycle. Woo order uses Woo's standard status and does not establish service confirmation or ticket issuance. No raw card data or credentials in logs, analytics, frontend or messages; encrypt secrets under operational key management, restrict rotation access and redact provider responses.

Before choosing a provider, obtain merchant agreement, official current technical documentation, sandbox and production credentials/eligibility, official callback authentication/verification rules, amount unit/limits, cancellation/refund and reconciliation interface, support/SLA, versioned plugin source and compatibility evidence. Security-review the adapter and test exact target WordPress/WooCommerce versions, HPOS and Checkout Blocks as well as any separately claimed classic checkout. No provider API, legal permission, plugin feature or pricing is asserted. Woo documents that Block payment integration is separate from gateway processing ([official guide](https://developer.woocommerce.com/docs/block-development/extensible-blocks/cart-and-checkout-blocks/checkout-payment-methods/payment-method-integration/), retrieved 2026-11-17); access Woo orders through CRUD for HPOS ([recipe book](https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/), same date).

## 2. Payment contract and operations
**WF-PAY-001:** signed-in customer accepts final Woo total → server checks hold and cart policy → create attempt with unique idempotency key and expected amount/currency → initiate provider transaction after local commit → customer returns/callback received → independently verify using provider-specific approved method → compare merchant, transaction, amount, currency and order linkage → atomically mark verified once and emit outbox → update Woo order via supported API → booking remains pending agency confirmation. Callback/redirect itself is not proof; prevent duplicate side effects, require reconciliation for unknown or mismatched attempts. Never hold a local DB transaction while calling provider. Local ledger entries and supplier fulfillment are separate.

If registration close applies, ordinary admission was already accepted by a valid hold; TTL min(10 minutes, close-now), deadline equals hold expiry. Independent verification completed locally at or before the deadline can consume a still-allocated hold without provider `paid_at`. After the deadline, require trustworthy provider `paid_at` at or before the deadline and a still-unreleased allocation. If released, transition booking `expired → exception` with prior expiry retained in audit; allocation remains released and payment remains verified. Route to manual refund review without new admission or automatic reclaim. Untrusted payment time after deadline requires manual exception. Staff audit corrections, retries and refunds. **UI-PAY-001** displays exact IRR, explicit optional toman (10 IRR = 1 toman), provider and pending/verified/unknown state. **API-PAY-001** callback is a proposed local ingress with provider-specific signature/lookup verification, replay protection and idempotent correlation; no assumed vendor endpoint. Support can view masked transaction reference and state; finance can authorize refund; customers see only their payment.

## 3. Fictional scenario H — domestic checkout
A hypothetical ZarinPal sandbox adapter is selected for this fictional scenario only; no real sandbox access, merchant eligibility, API behavior, compatibility or refund capability is asserted. One event seat costs 10,000,000 IRR (1,000,000 toman); Woo total and stored expected payment are 10,000,000 IRR. Customer signs in, obtains hold, sees terms and pays; hypothetical provider callback says successful. In this mock, independent local verification of merchant, reference, currency and amount completes before the deadline while the hold is allocated, so no provider timestamp is required; payment is marked verified, order paid, booking `paid_pending_confirmation`, and agency later confirms it. A post-deadline verification would require the trustworthy provider timestamp and still-unreleased allocation described above. Customer sees “Payment received; booking awaits confirmation” / «پرداخت دریافت شد؛ رزرو در انتظار تأیید است». If gateway expects another documented unit, conversion is configured once using exact integers and checked in contract tests. Crypto remains disabled and hidden absent independent legal and business approval; see [DOC-38](DOC-38_CRYPTO-PAYMENT-COMPLIANCE.md).

| Failure | Detection, UI, recovery, finance and audit |
|---|---|
| Wrong rial/toman unit | Compare expected integer amount and configured provider unit; reject verification, show payment under review, open finance exception; never silently accept 10× difference. |
| Duplicate callback | Unique attempt/provider reference; idempotent transition and one outbox event; acknowledge safely and audit duplicate. |
| Timeout/redirect without callback | Mark unknown, query via verified provider procedure and reconcile statements; do not report paid or retry charge blindly. |
| Amount, merchant or currency mismatch | Reject association, quarantine evidence and alert finance/security; no booking confirmation. |
| Verified payment after hold release | Transition booking `expired → exception` with prior expiry audited; allocation remains released and payment remains verified. Queue manual refund review, notify support/customer and do not create a new admission. |
| Payment succeeds, fulfillment fails | Keep verified payment and exception booking, offer resolution/refund per policy; never overwrite payment to failed. |
| Refund submitted but unconfirmed | Show pending refund, reconcile against authoritative provider evidence before succeeded; record retries. |

## 4. Tests and unresolved decisions
**TC-PAY-001** duplicate callback creates one verification and side effect; **TC-PAY-002** 10× mismatch blocks confirmation; **TC-PAY-003** timeout plus successful later inquiry converges without duplicate charge; **TC-REG-001** exact cutoff and released hold; **TC-PAY-004** refund succeeds independently of order/booking. Test credential rotation, tampered callback, spoofed return, replay, crash after provider success, Woo HPOS and supported Blocks/classic flows. Metrics: payment success, unknown age and reconciliation lag, aggregated without identifiers. **OPEN DECISION:** finance and integration lead select provider and finalize refund/settlement terms, approved unit conversion and trustworthy timestamp evidence. Legal counsel reviews eligibility before launch.
