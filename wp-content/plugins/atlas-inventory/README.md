# Atlas Local Inventory — internal operational preview

This separately installable plugin depends on active Atlas Core and domain Records registrations from Atlas Operations. Activation creates prefix-aware InnoDB resources, room nights and allocations with an idempotent versioned migration. It does not delete data on deactivation and never publishes availability, takes payments, confirms supplier bookings, runs vehicle dispatch or alters WooCommerce orders. Current project scope keeps customer stays/rentals request-only. All operational reads and writes are disabled unless `wp_get_environment_type()` is exactly `local` and `ATLAS_DEMO_MODE === true`; there is no production activation path. Operational deployment needs an independently implemented and reviewed authorization gate, supplier agreements, security review, tested backups and approved policy; this is not a production-readiness claim.

A staff user needs `atlas_manage_records`, an active membership in the owning organization, and access to the underlying core `unit_type` and `property` or `vehicle` record. An authorized agency admin may operate across organizations under Core's policy. Unit types require a property in the same organization with a named IANA zone. A whole villa has exactly one unit and cannot share its property with other registered room resources. Date intervals are local property dates `[check-in,check-out)`; vehicle instants are UTC `YYYY-MM-DDTHH:MM:SSZ` with exclusive end and a per-resource turnaround buffer. Changing the underlying property, whole-unit classification or zone prevents further operations until reconciled. A source unit count decrease blocks new allocations until capacity is reduced safely.

## Staff REST interface

Requests are JSON to `/wp-json/atlas-inventory/v1/`, authenticated as a WordPress staff user, with a valid `X-WP-Nonce` for `wp_rest`. The nonce is CSRF protection; record and organization authorization is checked again in the service. `POST /resources` accepts `record_type` (`unit_type` or `vehicle`), `record_id`, integer `min_stay`, and integer `turnaround_minutes`. The returned internal ID is used with `GET /resources/{id}` and the following POST endpoints:

- `/stay`: `resource_id`, `check_in`, `check_out`, integer `quantity`, unique `reference`; optional `request_id` must be an accessible core `stay_request` for the same property.
- `/vehicle`: `resource_id`, UTC `start_utc` and `end_utc`, `kind` (`rental`, `transfer` or `maintenance`), unique `reference`; optional `request_id` must be an accessible core rental/transfer request. Maintenance does not accept a customer request.
- `/capacity`: `resource_id`, integer `capacity`, integer `min_stay`; never exceeds core unit count or drops below allocations. `/blackout`: `resource_id`, `start_date`, `end_date`, boolean `blocked`; allocated nights cannot be blacked out.
- `/start`: `allocation_id` records an eligible rental pickup with its actual immutable server timestamp. `/return`: `allocation_id`, UTC `actual_utc`, `inspection`, boolean `disputed`; a return cannot precede the recorded actual pickup, and late return blocks conflicting upcoming allocations. `/release`: `allocation_id` releases unstarted allocation exactly once. `/resolve-dispute`: `allocation_id`, required reason; agency only.
- `/reconcile-pickup`: `allocation_id`, UTC `picked_up_utc`, required reason; agency only. Schema v2 deliberately leaves legacy pickup evidence NULL instead of inventing it from the planned start or update time. An in-use legacy allocation remains unavailable for new assignment and cannot be returned until authorized staff record reviewed pickup evidence through this explicit audited action. Existing pickup evidence cannot be overwritten through it.
- `/rental-policy`: `resource_id` and `policy` object containing opaque `policy_reference`, explicit integer `minimum_age`, opaque `coverage_reference`, and exact UTC `valid_until`. Agency only. Schema v3 snapshots the canonical vehicle category and licence class; car/motorcycle/van records must specify their required class. The code supplies no legal age, class or insurance rule. The agency must obtain and review the applicable policy. A legacy unclassified resource needs this explicit reviewed configuration before new allocation or handover. A reviewed policy cannot change while active rental allocations remain; resolve or release them first.
- `/eligibility-review`: `allocation_id` and a `review` object containing opaque `renter_reference`, integer `age_years`, `age_evidence_reference`, `coverage_evidence_reference`, and `review_reference`. For car/motorcycle/van additionally supply `license_class`, exact UTC `license_expires_at`, and opaque `license_evidence_reference`. Agency only. Approval records reviewer/time, policy hash and references; changed evidence requires release and a new unstarted allocation, not silent rewriting. The vehicle cannot be handed over without a current policy and this review, and licence expiry is rechecked at the actual pickup instant. Bicycle policy still requires reviewed age/coverage evidence but collects no unnecessary licence fields. These are manual operator attestations, not government identity, licence or insurer verification.

Each operation is audit logged, its database transaction locks the resource before its children and makes no network call. Every night in a requested stay is processed in order in one transaction; conflict rolls back all nights. Stay and vehicle allocation retry only SQL concurrency errors 1020, 1213 and 1205, capturing the numeric code before rollback, using at most three fresh transactions with 10/20ms backoff. Each attempt repeats authorization, resource, capacity and idempotency checks; unknown errors fail closed. Decision reads after the resource mutex are locking current reads rather than an older repeatable-read snapshot. Vehicle start/end intervals include turnaround; a vehicle in use or disputed blocks new allocations, and late return records a conflict rather than silently handing it over. Disputes do not initiate a charge. `reference` is an opaque idempotency key (8–120 safe characters), never personal information; retries with changed input fail. Optional core request IDs must not be invented. Actor-specific permissions are revalidated on every request, not cached.

## Limitations and checks

No public endpoint, live supplier inventory, scheduled hold expiry, actual supplier confirmation, automated identity/licence/insurance verification, photo uploads, deposits or automatic finance actions are implemented here. Manual policy/age/coverage/licence review checks are coded, with missing/expired/unauthorized cases; opaque references must point to an independently reviewed private evidence process, never raw licence numbers or documents in this database. Inspection text must be minimal and subject to an approved retention/access policy. The integration script includes a synchronized two-process last-room test and pickup/eligibility regressions; the existence of those tests is not a passing execution result. Role isolation, backup/restore, API nonce security and contract approval remain release gates. Run `wp eval-file tests/inventory-integration.php` only on an isolated local site after enabling Core, Operations and this plugin; the test creates and removes owned synthetic fixtures and leaves audit rows. The author did not execute its suites while editing.
