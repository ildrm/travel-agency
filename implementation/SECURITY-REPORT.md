## Actual authorization contract

WordPress capability is a ceiling, not an organization membership. Recognized membership roles are `viewer` (read only) and `contributor`, `editor`, `leader`, `manager`, `partner_admin`, `owner` (read/write draft baseline). These names are scoped application roles; they do not grant WordPress administrator, finance, agency approval, verified professional status or legal authority. Unknown roles fail closed. Both organization and membership must be active/approved as applicable. Per-type `organization_roles` may narrow read/write; a supplied map with an omitted operation or empty list denies that operation to partners. A schema cannot broaden a viewer into a writer.

The implementation's explicit initial agency override is a signed-in WordPress user with `manage_options`. This deliberately remains a high-trust technical authority; real agency staff/finance delegation, separation of duties, provisioning and human risk acceptance must be reviewed before production. A person who is editor in A and viewer in B must select and satisfy B's effective authority for B's records. Record ownership is immutable through ordinary update paths.

Authenticated REST transport uses WordPress cookie/nonce handling plus independent actor/object/role policy. A nonce is not permission or anti-replay. Internal `rest_do_request` fixtures test server dispatch; the separate recorded headless browser scenarios exercise authenticated transport and the booking/payment/agency flow. Neither establishes exhaustive CSRF or session-security coverage. Private booking, queue and traveler responses use no-store projections; public offer data excludes private records/costs.

A focused source check of partner review/membership, support reply/triage, enrollment linking and finance UI found no public Core record/finance mutation called inside a caller-owned `START TRANSACTION`. Partner/support/enrollment use direct writes plus transaction-neutral audit/outbox helpers, and perform record reads after commit or rollback. Finance approval uses connection advisory locks around Core's own transaction, with explicit recovery for the committed-approval/request-mapping window. This bounded check is not an exhaustive review of every plugin callback or future caller.

## Payment, refund and provider trust boundary

All three domestic gateway classes are unavailable server-side and reject forced use. They are disabled interfaces awaiting actual merchant specifications, eligibility, credentials and authorized acceptance, **not implemented or verified live PSP adapters**. There is no invented external endpoint, signature or refund capability. Digital-asset activation is not provided.

The service gateway allowlist is enforced on the server for classic checkout, order-pay and Store API payment dispatch. Enabling Woo's BACS/COD or an unrelated gateway does not authorize it to collect Atlas service money. Store API payment-context guarding covers existing-order dispatch independently of whether a cart is present. This active-plugin policy does not claim protection against an administrator deactivating or modifying required application plugins; deployment dependency/readiness controls need their own evidence.

Atlas Core and Atlas Gateways declare `custom_order_tables` and `cart_checkout_blocks` compatibility from their main plugin bootstraps on WooCommerce's required `before_woocommerce_init` hook, with `WC tested up to: 11.3.0`. Recorded HPOS CRUD/Store API tests and the actual headless Blocks payment flow support this narrowly observed framework/local-simulator declaration. It does not enable or certify the disabled domestic PSP boundaries, and does not establish compatibility with other WooCommerce/PHP versions or third-party gateways.

The Woo simulator requires exact local environment plus explicit `ATLAS_DEMO_MODE === true` and authenticated ownership. Its results are fictional and transfer no funds. `VerifiedPayment`/`VerifiedRefund` are trusted server-only DTOs: their factories are not proof of real provider authentication. Every future adapter must independently establish merchant/order/reference/amount/currency/outcome before constructing them. No public route accepts a client `verified` boolean. Test clock/schema/audit fault hooks require PHP CLI, local environment and explicit test constant, and cannot be enabled by browser JSON.

The append-only signed IRR ledger is operational reconciliation data, not certified double-entry/statutory accounting. Refund approval is distinct from verified completion; partial/cumulative refunds are bounded against captured verified payment. The manual finance UI exposes exception/ledger review and request/approve operations, with no transfer-submission or public proof endpoint. A requested/approved refund creates no verified-refund debit. The simulated refund fixture does not prove an external refund, a WooCommerce refund object or a real bank transfer. Source and fixtures do not constitute merchant or finance signoff.

## Personal data and remaining security work

- Traveler names, birth dates and guardian declarations are self-declared owner-scoped records; they are not verified identity, age, guardianship, consent or legal eligibility. Data is stored in the application database; reviewed at-rest encryption/key management is not demonstrated. No protected-document upload service should be replaced with public WordPress media.
- Privacy export covers the implemented booking/traveler subset through WordPress's request workflow. Erasure currently reports manual retention review. Complete field-level retention, lawful basis, legal holds, data-recipient contracts and backup propagation remain unapproved.
- Denied private/cross-organization reads are not consistently recorded as audit events. Add privacy-safe, abuse-resistant denial auditing and alert routing; existing indistinguishable denials are not a substitute for this observability requirement.
- Full MFA, login/recovery abuse protection, short-lived invitations/delegated support access, sensitive-file scanning/download, secret rotation, independent SAST/DAST/penetration review and incident exercises remain incomplete or externally unverified. No independent vulnerability-clean claim is made.
- Per-type role policies and agency provisioning need review across every module, export, cache, worker and UI. Generic mechanisms plus representative fixtures do not prove complete field/endpoint coverage.
- The English and Persian checkout axe artifacts each retain a critical-impact incomplete `aria-valid-attr-value` check requiring manual investigation: [English checkout](evidence/axe-checkout-en.json), [Persian checkout](evidence/axe-checkout-fa.json). Passing browser assertions and zero reported automatic violations do not close this incomplete result or constitute accessibility approval.
- Real provider unknown/timeout/reconciliation, callback signatures, currency-unit contract, supplier issuance/disruptions, chargebacks, partner settlement, payout evidence and production recovery require actual interfaces and further implementation/testing. Missing local functionality must remain marked incomplete rather than relabeled external approval.
- The tested small race harness is not the requested 100-concurrent-request peak-load evidence. Expensive tests were kept off the active user's workstation. Local archive-install and restore checks passed; production-like capacity, infrastructure/secret/file recovery, real prior-version upgrades and external-event reconciliation still need recorded evidence.
