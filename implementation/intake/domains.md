## Shared invariants and integration needs

- One agency site, users may belong to many orgs. Enforce authentication, role capability, active membership and target ownership/purpose on each read/write/export/file/worker; no client org ID alone, no nonce-only authorization (DOC-23 §§1–4). Deny and redact failures; audit sensitive events without PII/secrets. Public RFQ submissions can be anonymous with abuse limits, but later access needs verified owner or authorized org (DOC-26 §2). Parent core owns organization tables/ACL and authoritative enrollment/hold operations; wait for typed contracts before using them.
- Admission creates one hold for signed-in purchaser, open inclusive/close exclusive, TTL min(10 minutes, close-now). Cohort enrollment references existing accepted hold and never allocates a second seat. Local independent verification by deadline can consume allocated hold without provider timestamp; after deadline require trusted provider paid_at ≤ deadline and unreleased allocation. If released, transition booking expired→exception, retain expiry audit, allocation released, payment verified, manual resolution/refund with no new admission (DOC-30/31/37). Parent core owns concurrency, outbox and Woo order integration; domain callers must not reimplement them.
- Woo order, payment attempt, supplier reservation, booking, ticket, refund and payout remain distinct. Woo CRUD/HPOS, source-of-truth Woo total, integer IRR, 10 IRR = 1 display toman; no floating-point payable amounts; provider units unknown until contract review. No network call during local transaction. No card details/secrets in storage/logs. Any provider callback requires verified provider contract and server-side independent verification; redirect is insufficient.
- All REST methods below proposed internal interfaces. Never claim provider endpoint or capability without official and merchant-specific verification. Safe blocked gateway boundaries, no live requests, no fake confirmation, and no crypto checkout. English/Persian, semantic labels, keyboard, error/status messages and RTL needed; quotes and transport stay request-only when contracts absent. Test critical negative paths and persist actual data when implemented.

## Conflicts and decisions requiring coordination

1. Implementation prompt §4.2 suggests many separate plugins; parent assigns a smaller `atlas-operations` and separate `atlas-gateways`. Prompt itself permits fewer coherent deployed plugins. Logical separation and activation dependencies still need shared ADR and test coverage.
2. Prompt §10.2 `PSP-AMOUNT-13` says expired hold cannot mark paid, whereas DOC-30/31/37 distinguish independently verified late money from entitlement: preserve verified payment and booking `expired → exception`, allocation released, no admission/automatic reclaim. Recommend interpret “cannot mark paid” as cannot mark booking/order fulfilled or grant admission solely by callback; parent to decide exact Woo order/payment representation and record ADR. Do not reject real verified payment fact.
3. Prompt requests all three fully integrated PSPs and sandbox fixture coverage; DOC-37 selects one only after evidence and provider APIs/eligibility are unknown. Implement safe disabled interface/options/negative paths; external methods `BLOCKED_EXTERNAL` until current official merchant contracts, documented authentication/verification, amount and refund semantics and credentials are available. Never invent endpoint or claim sandbox tested.
4. Prompt asks full future-domain implementation; docs restrict MVP selling stay/transport/rental and live ticket issuance. Implement feasible management/request/procurement features but keep unapproved commercial execution and external connectivity gated; proposed milestone phase must not imply activation.
5. Prompt’s state examples are suggestions, canonical docs define booking/hold/payment/refund separately; parent must publish exact persistence interface and event contract. No module may independently change inventory, payment or Woo order state.
6. API-ACA-001 depends on accepted hold and parent core authorization/object models; API-XFER-001 public anonymous RFQ needs replay-safe idempotency and abuse controls but subsequent access only after identity ownership. Agree endpoints, WP auth/capability names, private storage, schema migrations, response/error envelope, outbox and test harness before implementation.
7. DOC-35 requires art scan/private files and DOC-36 KYB, yet no scanner/private storage or retention policy is supplied. Do not upload sensitive documents into public media as a shortcut; scope a safe disabled upload capability until backend is reviewed.
8. Policy and legal/financial language, supplier/PSP terms, tax, accessibility and Persian legal copy require real human validation. No generated example is a deployed capability, verified price, legal permission, insurance or approved contract.
